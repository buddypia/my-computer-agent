# Computer Use の実機受け入れ

`swift test` の成功は実機操作の成功を意味しない。`ContextMCPServerComputerUseTests` は固定画像と
DryRun入力、`TwoTierAutonomousLoopOfflineE2ETests` は模擬画面・模擬入力を使う。
それらの回帰防止は維持し、実画面・実入力・実モデルの証拠を別に測る。

## 案の比較と選択

| 案 | 確かめられること | 限界 |
|---|---|---|
| ユニットテストを追加 | 境界条件、拒否、取消、座標変換 | OS権限、イベント配送、視覚判断は測れない |
| 録画・固定画面の再生 | 判断を安く繰り返し比較 | 実入力で画面が変わる因果関係がない |
| 固定手順で実機操作 | 本番MCP、撮影、座標変換、OS入力、実UIの状態変化 | 画面の理解とモデルの計画能力は測れない |
| 実モデルで実機タスクを完遂し独立採点 | 目標→視覚判断→実操作→再観測→結果報告 | 実行環境とAPIが必要、費用と揺れがある |

最後の案を能力評価に採用し、固定手順のsmokeを故障切り分けに併用する。
初期課題は、ユーザーデータを使わない独立したAppKit注文フォーム。
本番CLIを別プロセスのstdio MCPとして起動し、`computer` の実実装をそのまま呼ぶ。
実行にモック・dry runへのfallbackはない。

## 実行

GUIログイン中のmacOS、Swift 6、Python 3の標準ライブラリを使う。ブラウザは起動しない。
起動元アプリ/ターミナルにAccessibilityとScreen Recordingの許可が必要。
OSの許可は変更しない。不足は `blocked` と非ゼロ終了で残す。

```bash
swift build

# まず撮影・実入力・状態変化を固定手順で切り分ける（モデル能力の点数ではない）。
python3 -B Scripts/eval/computer-use/run.py --live --mode smoke \
  --output artifacts/computer-use/smoke-001

# 画像と目標だけを実モデルに渡す。モデルIDは明示し、fallbackで置き換えない。
secret run GEMINI_API_KEY -- python3 -B Scripts/eval/computer-use/run.py \
  --live --mode agent --model gemini-3.8-flash \
  --output artifacts/computer-use/agent-001

# 入力を全く送らない対照試験。期待結果は failed、終了コード1。
python3 -B Scripts/eval/computer-use/run.py --live --mode no-input --trials 1 \
  --output artifacts/computer-use/no-input-001
```

出力先は新しいディレクトリでなければ拒否する。既存の証拠を上書きしない。
既定はランダムなコード・配置で3試行。`--trials` で1〜20試行を指定できる。
1試行150秒、モデル16ターン、24アクションが既定の上限。
CLIは `--mca <binary>` で検証対象を指定できる。対象バイナリは `mcp --config <file>` に対応している必要がある。

実行中は不透明な専用ウィンドウが主ディスプレイを覆う。他の作業と並行して実行しない。
Escで中断を要求し、Ctrl+Cでrunnerを中断できる。モデルのAPI応答待ち中のEscは次の観測時に処理する。
Esc後も専用画面を保ち、MCP停止後に閉じることで、処理中の入力が背後へ漏れるのを避ける。
前面アプリの変化でも中断する。fixtureは240秒で自動終了し、runnerは自分が起動した
プロセスだけを回収する。既存アプリ・ブラウザタブを終了しない。
試験用configとDBは証拠ディレクトリ内に作り、通常の設定・履歴DBは変更しない。

## 成功の定義

モデルの成功宣言、MCPの「クリックした」というテキスト、接続成功だけでは合格しない。
別プロセスのAppKitアプリから得た事後状態で、次のすべてを照合する。

1. 画面に表示されたランダムな注文コードが正確に入力され保存されている。
2. 実テキスト変更通知と確認チェックの操作が記録されている。
3. 保存は試行・成功とも正確に1回。
4. 保存イベントで初めてランダムなレシートが生成される。
5. 保存後に本番MCPから新しいスクリーンショットを取得している。
6. モデルの最終回答がそのレシートと完全一致する（agentモードのみ）。

モデルに渡すのは目標、公開MCPスキーマから絞った `computer` ツール、実画像とツールの実結果だけ。
採点用のコード・座標・レシート・fixture状態は渡さない。モデルにはshell、AX、ファイル読取などの迂回路がない。
公開アクションは `screenshot` / `left_click` / `type` / `wait` に限定し、修飾キーや画面端のクリックを拒否する。
smokeは意図的に座標と注文コードを使うので、agent成功率と分けて報告する。

## 証拠と終了コード

`report.json` にmode、課題の範囲、モデルID、要求試行数、各試行の結果、成功率を保存する。
blocked・中断・試行不足の場合、成功率は `null` とし、0%の能力評価に読み替えない。
`scored_trials` はpassed/failedとして採点できた試行数。全要求試行が合格した場合だけrun全体をpassedにする。
git HEAD・dirty状態と、MCAバイナリ・runner・fixtureソース/バイナリのSHA-256も記録する。
各trialの `result.json` に実ツール引数、経過時間、独立事後状態、最終回答、判定項目と失敗理由を保存する。
実スクリーンショットはJPEGとして保存する。APIキーとモデルの内部思考は保存しない。
ローカル証拠は作者が書き換え可能であり、改ざん耐性のある証明ではない。
自己採点の記録だけでTrust承認や一般的な出荷可否を決めず、レビューと実行条件を合わせて確認する。

| 終了コード | 意味 |
|---|---|
| 0 | 要求した全試行で全判定項目に合格 |
| 1 | タスク失敗、予算超過、MCP/fixtureの実行失敗 |
| 2 | 権限・API資格情報・起動環境などの前提不足 |
| 130 | オペレーターが中断 |

通常CIは採点器の正例・反例、stdio通信、実行opt-inを検査しfixtureをコンパイルする。
GUI操作も実モデル呼出しも行わず、CI緑を実機合格として扱わない。
ローカルの採点器テストは `secret sandbox -- python3 -B Scripts/eval/computer-use/test_runner.py`。

## 証明範囲

この課題が測るのは「外部MCPクライアント→MCA→ネイティブフォーム」の閉ループ。
合格してもCopilotのルーティング・承認カード・Stop伝播、ブラウザ、スクロール、ドラッグ、
会議観測、複数ディスプレイ、一般アプリの全タスクの受け入れにはならない。
3/3のような少数試行を一般的な成功率と解釈しない。OS/モデル/バイナリが変われば再測定する。
実機の結果は [初回検証記録](computer-use-initial-results.md) に記載する。
